# Requirements Document

## Introduction

The Booking Heatmap feature adds a 24-hour geographic heatmap visualization to the SaktoGo admin dashboard. The heatmap displays ride booking density across Olongapo City and Subic Bay, highlighting peak-hour hotspots using weather-forecast-style color gradients. It consumes the synthetic ride-hailing dataset (generated by `generate_dataset.py`) to show where and when customers book rides throughout the day.

## Glossary

- **Heatmap_Renderer**: The frontend component responsible for drawing the geographic heatmap layer on the Leaflet map
- **Dataset_Loader**: The backend module that reads and aggregates the ride-hailing CSV dataset for heatmap consumption
- **Admin_Dashboard**: The admin-mode interface of the SaktoGo application, accessed via the "Enter as Admin" entry point
- **Time_Slider**: A UI control that allows the admin to select a specific hour (0–23) to filter the heatmap display
- **Intensity_Scale**: The color gradient legend that maps booking density values to colors, ranging from cool (low density) to hot (high density)
- **Booking_Density**: The count of ride pickups within a geographic cell for a given hour or time range
- **Peak_Hours**: Time periods with the highest booking concentration, defined as 6:00–9:00 AM (morning) and 5:00–8:00 PM (evening) per the existing dataset configuration

## Requirements

### Requirement 1: Dataset Loading and Aggregation

**User Story:** As an admin, I want the system to load and aggregate the ride-hailing dataset, so that booking density data is available for heatmap rendering.

#### Acceptance Criteria

1. WHEN the admin dashboard is opened, THE Dataset_Loader SHALL read the ride-hailing CSV file and parse all ride records into memory, expecting columns: ride_id, ride_date, pickup_latitude, pickup_longitude, dropoff_latitude, dropoff_longitude, pickup_time, dropoff_time, and weather_condition
2. WHEN the dataset is loaded, THE Dataset_Loader SHALL overlay a grid of 0.002-degree square cells onto the geographic bounds of the dataset and aggregate the count of pickup coordinates falling within each cell per hour of day (0–23), producing a Booking_Density integer value representing the number of pickups in that cell for that hour
3. IF the CSV file is missing, THEN THE Dataset_Loader SHALL return an error message indicating the file could not be found
4. IF the CSV file is present but contains rows with missing required columns or non-numeric latitude/longitude values, THEN THE Dataset_Loader SHALL skip those malformed rows and log a warning, continuing to process valid rows
5. THE Dataset_Loader SHALL expose an API endpoint that accepts an hour parameter as an integer between 0 and 23 inclusive and returns the aggregated heatmap data containing cell center coordinates and their corresponding Booking_Density values for that hour
6. IF the requested hour parameter is not an integer between 0 and 23 inclusive, THEN THE Dataset_Loader SHALL return an error message indicating the hour value is invalid
7. WHEN the API endpoint returns aggregated heatmap data, THE Dataset_Loader SHALL respond within 2 seconds of receiving the request

### Requirement 2: Heatmap Visualization Rendering

**User Story:** As an admin, I want to see a color-gradient heatmap overlaid on the map, so that I can visually identify where most bookings occur.

#### Acceptance Criteria

1. WHEN aggregated booking data is received from the Dataset_Loader API endpoint, THE Heatmap_Renderer SHALL draw a heat layer on the Leaflet map using the pickup coordinates and their associated Booking_Density values as intensity weights
2. THE Heatmap_Renderer SHALL use a color gradient progressing from blue (low density) through green and yellow to red (high density), with a minimum of 4 discrete color stops distributed evenly across the intensity range
3. WHEN no bookings exist for the selected hour, THE Heatmap_Renderer SHALL remove the heat layer from the map and display a visible notice on the map area indicating no data is available for that time slot
4. WHEN the selected hour changes, THE Heatmap_Renderer SHALL replace the existing heat layer with updated data within 500 milliseconds without a full page reload
5. IF the API request to fetch aggregated booking data for the selected hour fails, THEN THE Heatmap_Renderer SHALL retain the previously displayed heat layer and display a notice indicating the data update failed

### Requirement 3: Time-of-Day Selection

**User Story:** As an admin, I want to select a specific hour of the day, so that I can see how booking patterns shift throughout a 24-hour cycle.

#### Acceptance Criteria

1. THE Admin_Dashboard SHALL display a Time_Slider control implemented as an HTML range input that allows selection of any integer hour from 0 to 23
2. WHEN the admin releases the Time_Slider at a new hour value, THE Heatmap_Renderer SHALL update the displayed heatmap to reflect Booking_Density for the selected hour within 500 milliseconds
3. THE Time_Slider SHALL display the currently selected hour in 12-hour format with AM/PM suffix (e.g., "6:00 AM", "12:00 PM", "5:00 PM")
4. WHEN the admin dashboard loads, THE Time_Slider SHALL default to the current hour of day in Asia/Manila timezone
5. THE Time_Slider SHALL be operable via keyboard arrow keys, incrementing or decrementing the hour by 1 per key press
6. IF the API request triggered by a Time_Slider change fails, THEN THE Admin_Dashboard SHALL display an error notice and retain the previously displayed heatmap data

### Requirement 4: Intensity Scale Legend

**User Story:** As an admin, I want to see a color legend on the map, so that I can interpret the heatmap colors and understand relative booking density.

#### Acceptance Criteria

1. THE Admin_Dashboard SHALL display an Intensity_Scale legend overlaid on the bottom-right corner of the map, showing the color gradient from blue (low) through green and yellow to red (high) matching the Heatmap_Renderer color mapping
2. THE Intensity_Scale SHALL label the minimum end as "Low" and the maximum end as "High"
3. WHEN the heatmap data updates due to a Time_Slider change, THE Intensity_Scale SHALL remain continuously visible without disappearing or flickering, and SHALL display the same color gradient currently applied to the heat layer
4. THE Intensity_Scale SHALL have a minimum width of 200 pixels so that the gradient transitions are distinguishable

### Requirement 5: Peak Hour Indicators

**User Story:** As an admin, I want peak hours to be visually marked on the time slider, so that I can quickly identify high-demand periods.

#### Acceptance Criteria

1. THE Time_Slider SHALL visually highlight the morning peak hours (6:00–9:00 AM) using an orange background segment and the evening peak hours (5:00–8:00 PM) using a red-orange background segment on the slider track
2. WHEN the admin selects a peak hour, THE Admin_Dashboard SHALL display a label indicating "Morning Peak" or "Evening Peak" alongside the time display, corresponding to the selected range
3. WHEN the admin selects a non-peak hour, THE Admin_Dashboard SHALL not display any peak label alongside the time display
4. THE Time_Slider peak segments SHALL be rendered as colored regions on the slider track that are visible regardless of the current slider thumb position

### Requirement 6: Admin Dashboard Integration

**User Story:** As an admin, I want the heatmap to be accessible from the existing admin interface, so that I do not need a separate application to view booking patterns.

#### Acceptance Criteria

1. WHEN the admin enters the application via "Enter as Admin", THE Admin_Dashboard SHALL display a navigation element labeled "Booking Heatmap" that switches the view to the heatmap mode
2. THE Admin_Dashboard SHALL display the heatmap on the same Leaflet map instance used by the existing route-finder interface, preserving the current map center and zoom level when switching between views
3. WHEN the admin switches to the heatmap view, THE Admin_Dashboard SHALL hide the passenger ride-request controls (ride type picker, pickup/drop-off buttons, driver offer card) and the simulated driver markers, and show the heatmap controls (Time_Slider, Intensity_Scale)
4. WHEN the admin switches away from the heatmap view, THE Admin_Dashboard SHALL remove the heat layer from the map, restore the ride-request controls and simulated driver markers, and return the map legend to its default driver-status display
5. IF the heatmap data fails to load when the admin switches to the heatmap view, THEN THE Admin_Dashboard SHALL display an error notice indicating the heatmap data is unavailable and keep the navigation element accessible for retry

### Requirement 7: Dataset Generation Compatibility

**User Story:** As a developer, I want the heatmap to work with the existing dataset generator, so that sample data is readily available without additional tooling.

#### Acceptance Criteria

1. THE Dataset_Loader SHALL consume the CSV file named `ride_hailing_dataset.csv` produced by `generate_dataset.py` without requiring modifications to the generator script
2. THE Dataset_Loader SHALL parse the `pickup_time` column in HH:MM:SS format and extract the hour component (0–23) to associate each record with an hour-of-day for Booking_Density computation
3. THE Dataset_Loader SHALL use the `pickup_latitude` and `pickup_longitude` columns as geographic coordinates for each record's heatmap position
4. WHEN the dataset contains records spanning multiple dates, THE Dataset_Loader SHALL aggregate all records by hour-of-day regardless of the `ride_date` value, producing a single 24-hour density profile
5. IF the CSV file is missing any of the required columns (`pickup_latitude`, `pickup_longitude`, `pickup_time`), THEN THE Dataset_Loader SHALL return an error message indicating which columns are absent
